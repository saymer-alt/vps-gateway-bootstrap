# Gemini Web на Android через Mihomo VPS — полевые наблюдения (07.11.2026)

> **Статус: OBSERVED / INVESTIGATION OPEN.** Это дополнение к [ручному профилю эшелонированного выхода](mihomo-manual-tiered-egress-se2.md), не новый конфиг и не доказанный root cause. Наблюдения основаны на присланных владельцем состояниях API Mihomo и журналах `/connections`; прямого доступа автора к VPS не было. Документ **не разрешает** live-мутации и не меняет Core MVP, установщик, генератор или существующий fail-closed контракт.

## Симптом и границы наблюдений

- Клиент: Android, **Chrome Web** (`https://gemini.google.com/`), не отдельное приложение Gemini.
- Домашний Mihomo автоматически выбирает выход, включая цепочку через VPS. Для диагностики выход VPS фиксировали вручную. При выборе **другого, нидерландского выхода непосредственно в домашнем Mihomo** Gemini на том же Android открывался. Это существенно снижает подозрение на сам MagiTrickle, но **не доказывает**, что он вообще не влияет на другие режимы.
- На ПК Gemini открывается через проблемный VPS; на Android через часть VPS — сначала сообщение о недоступном регионе, позднее «Что-то пошло не так (1)» / при создании чата — «Неизвестная ошибка».
- **Инкогнито без входа** открывает веб-сайт; после авторизации тем же Google-аккаунтом на проблемном маршруте возникает ошибка (1). Это наблюдение об авторизованной сессии; не доказательство блокировки аккаунта или нарушения условий подписки.
- На SE2 авторизованный чат Android позднее **начал работать**, без подтвержденного изменения набора доменных правил. Временна́я связь с переключением `GLOBAL` не является доказательством причины.

| Факт | SE (`Saymer`) | SE2 (`Saymer2`) | EE (`hungry-boyd`) |

| `AUTO-EXIT.now` | `WARP SE` | `WARP SE2` | `WARP-WG-EE-1` |
| `GEODEMA.now` в начале | `GEO \| 🇳🇱 Hysteria 2 \| Нидерланды` | `GEO \| 🇫🇮 ⚡ Финляндия` | `🇵🇱 ⚡ Польша` |
| Доступность групп | API `alive: true` | API `alive: true` | API `alive: true` |
| Итог мобильного Gemini | «Что-то пошло не так (1)» | Сначала ошибка, позднее чат работает | «Что-то пошло не так (1)» до сравнения с Финляндией |
| TUN/fake-IP по присланному YAML | есть, gVisor + fake-IP | **отсутствуют в присланном YAML** | есть, gVisor + fake-IP |

Состояние EE **после** теста: `GEODEMA.now=🇫🇮 ⚡ Финляндия`, `fixed=''`, `alive=true`. Автоматический выбор восстановлен, хотя `url-test` по-прежнему выбрал Финляндию. **Нет подтвержденного E2E-теста авторизованного Gemini через EE после этого выбора**, поэтому нельзя записывать Финляндию как решение для EE.

## Что действительно видно в /connections

**SE2, 16:12–16:23 MSK:** `gemini.google.com`, `gemini.gstatic.com`, `waa-pa.clients6.google.com`, `geminiweb-pa.clients6.google.com` и `proactivebackend-pa.googleapis.com` наблюдались с цепочкой `GEODEMA` → выбранный финский узел. `signaler-pa.clients6.google.com`, `ogads-pa.clients6.google.com`, `play.google.com`, `www.gstatic.com` и другие общие Google-хосты шли через `WARP SE2`. После изменения `GLOBAL` в логах появилась ожидаемая цепочка `WARP SE2 > AUTO-EXIT > GLOBAL` вместо прежней `WARP SE2 > GLOBAL`. Основной выход WARP при этом **не сменился**.

**SE, 16:26–16:29 MSK:** `gemini.google.com`, `gemini.gstatic.com`, `waa-pa.clients6.google.com`, `optimizationguide-pa.googleapis.com` шли через `GEODEMA` → NL Hysteria2. `signaler-pa.clients6.google.com`, `ogads-pa.clients6.google.com`, `accounts.google.com`, `www.google.com`, `www.googleapis.com`, `play.google.com` шли через `WARP SE > AUTO-EXIT > GLOBAL`. Во время данного интервала `geminiweb-pa.clients6.google.com` **не наблюдался** — не заключать, что этот endpoint не использовался вообще: `/connections` — выборка **активных**, а не завершённых соединений, часть трафика может пройти до начала/между опросами.

**Необходимое различие:** работа сайта и активность прокси-цепочки — не доказательство успешного конкретного API-запроса или отсутствия ошибки на стороне Google. Мониторинг не показывает URL path, HTTP status, ответ приложения, а многозадачный Android генерирует фоновые обращения не только от Chrome. Совпадение по времени не доказывает, что конкретный общий Google-домен вызвал ошибку.

## Выводы без поспешного исправления

1. **Гипотеза «пропущен домен» остаётся открытой**, но данных недостаточно для добавления новых rules: и на успешном SE2, и на проблемном SE вспомогательные Google-домены проходили через WARP. Особенно не делать blanket `DOMAIN-SUFFIX,google.com` / `googleapis.com` / `gstatic.com` → GEODEMA.
2. **Смешение exit IP** для авторизации/общих Google-сервисов (WARP) и Gemini (Geodema) может иметь значение, но causal E2E/A-B проверка ещё не проведена. Аналогично регион/ASN выбранного Geodema и особенности Google-аккаунта — лишь гипотезы.
3. **TUN/gVisor/fake-IP** присутствуют на SE и EE и отсутствуют в YAML SE2. Это наблюдённая корреляция, **не причина**: поток через явный `mixed-port:7890` не обязательно проходит через TUN. Нельзя менять TUN/DNS/AMG policy-routing ради непроверенной гипотезы.
4. **`GLOBAL` — селектор, а не `mode: global`.** На SE2 `profile.store-selected:true` совместим с восстановлением прежнего ручного выбора `WARP SE2`, обойдя `AUTO-EXIT` для `MATCH,GLOBAL`. При фактическом PUT `/proxies/GLOBAL` с `{"name":"AUTO-EXIT"}` получены `HTTP 204` и `GLOBAL.now=AUTO-EXIT`. Это восстанавливает **маршрут через группу fallback**, но само по себе не меняет выбранный WG и не доказывает исправление Gemini.
5. **Geodema — provider-подписка на множество узлов, не один сервер.** `url-test` умеет выбирать доступный узел по network/latency check, но `generate_204` не тестирует авторизованный Gemini, страну по Google или применимость entitlement аккаунта. `empty-fallback: REJECT` — элемент политики, а не полное подтверждение fail-closed в negative E2E.
6. Пользователь сообщил временную связь с подключением недорогой промоподписки Google AI к своему аккаунту. **Причинная связь не установлена**; не включать конкретные аккаунты, суммы и данные продавца в репозиторий.

## Уроки из диагностических команд

- Запрос `GET /proxies/GEODEMA` показывает `now`, `fixed`, `alive`; `GET /proxies` даёт состояние всех групп. `GET /connections` с полями `metadata.host` / `rule` / `chains` и счётчиками позволяет наблюдать новые/активные TCP/UDP-соединения; скрипт с опросом 250 мс **может пропускать короткие соединения** и не видит HTTP-уровень.
- На SE вспомогательный запрос `GET /proxies/{url-encoded leaf node}` вернул **404** **до PUT**. Не считать, что всякий элемент `GEODEMA.all` обязательно доступен по этому маршруту API; для безопасного read-only discovery достаточно состояния группы; не делать предположений о состоянии прокси из 404.
- Скрипт с `python3 - <<'PY'` и последующим `input()` **не годится для интерактивной паузы**: stdin уже использован heredoc, `input()` вызвал `EOFError`. Блок `finally` всё же выполнил `DELETE /proxies/GEODEMA`; `fixed=''` подтвердил снятие ручной фиксации. Для будущих тестов использовать отдельные команды и **явное read-back**, проверять восстановление группы после эксперимента. `DELETE` снимает фиксацию, но **не гарантирует возврат к прежнему узлу**.
- Любая операторская временная смена группы через API — **живая мутация маршрутизации**, пусть и без YAML/restart. Не выполнять её автоматически, особенно на gateway с AWG/TUN, без отдельного owner GO и восстановления связности.
- Не сохранять публично: MASQUE/WG private keys, subscription URLs/tokens, HWID, Google cookies, аккаунтные идентификаторы, полный приватный YAML, live session dumps.

## Если возобновится диагностика (не выполнено / операторский план)

1. Зафиксировать **точную воспроизводимую матрицу**: тот же Android/Chrome/аккаунт, окно авторизации, SE против SE2/EE и отдельный домашний нидерландский выход; отмечать момент ошибки и выбранные узлы на протяжении теста (не менять несколько переменных за раз).
2. Перед любыми временными изменениями **read-only**: `GET /proxies` и `GET /connections`, проверить `GLOBAL.now`, `AUTO-EXIT.now`, `GEODEMA.now`, `fixed`, адресату сопоставлять только client-owned connections; анонимизировать данные.
3. В отдельном операторски одобренном узком A/B-тесте проверить одинаковый exit для основных Gemini и общих Google/auth endpoints **в рамках тестового клиента**. Откатить правила/выбор сразу после теста; **не** направлять весь домен Google через платную подписку в постоянном YAML.
4. При сохранении ошибки на одном exit сравнить на том же клиенте выбранные Geodema nodes, активные авторизованные запросы и (при наличии) браузерную диагностику без токенов/куки. Коды «(1)» сами по себе **не определяют root cause**.
5. **STOP:** не переписывать конфиги трёх VPS, не отключать Gateway TUN/DNS, не внедрять новую функцию в `link-generators`, не заявлять E2E/негативный fail-closed PASS до подтверждений. На ПК Gemini работает; сохранение текущего baseline предпочтительнее неподтверждённого исправления.
